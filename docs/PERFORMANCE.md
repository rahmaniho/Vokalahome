## ۲. ریشهٔ کند بودن نسخهٔ قبل

سه علت، به‌ترتیب اهمیت:

### ۲٫۱ `framer-motion` در بالای صفحه — ~۳۴ KB

نسخهٔ قبل بخش قهرمان صفحهٔ نخست را با `framer-motion` متحرک می‌کرد. این یعنی:

- کل کتابخانه در باندل **مشترک** می‌نشست، چون تقریباً هر صفحه چیزی از آن استفاده می‌کرد
- بخش قهرمان به یک کلاینت-کامپوننت تبدیل می‌شد، پس تا hydration کامل نشود متحرک نمی‌شد
- عنصر LCP (تصویر قهرمان) پشت این زنجیره صف می‌کشید

**راه‌حل:** حذف کامل کتابخانه. جایگزین‌ها:

| کاربرد قبلی | جایگزین |
| --- | --- |
| ظاهر شدن هنگام اسکرول | `IntersectionObserver` + `[data-reveal]` در CSS (کامپوننت `Reveal`) |
| باز و بسته شدن آکاردئون | `grid-template-rows: 0fr → 1fr` |
| شمارندهٔ عددی | `requestAnimationFrame` (کامپوننت `CountUp`) |
| ورود اولیهٔ عناصر | کلاس‌های Tailwind `animate-fade-up` / `animate-fade-in` |

همهٔ این‌ها `prefers-reduced-motion` را رعایت می‌کنند.

### ۲٫۲ کامپوننت‌های کلاینتی غیرضروری

`CustomCursor`، `LoadingScreen`، `ScrollProgress`، `FloatingMenu` و یک `Providers` سراسری
همگی `'use client'` بودند و در هر صفحه بارگذاری می‌شدند. `LoadingScreen` به‌طور خاص ضدالگو
بود: روی سایت استاتیک، HTML از لحظهٔ اول آماده است و نمایش اسپینر فقط LCP را عقب می‌اندازد.

هر پنج کامپوننت حذف شدند. صفحهٔ نخست حالا یک **سرور-کامپوننت** است؛ تنها بخش تعاملی آن
نشانگر «الان بازیم؟» است که چند صد بایت جاوااسکریپت دارد.

### ۲٫۳ تصاویر بدون فرمت مدرن

نسخهٔ قبل JPEG خام سرو می‌کرد. در حالت `output: export` بهینه‌ساز Next خاموش است، پس
`next/image` هیچ کمکی نمی‌کرد.

**راه‌حل:** `scripts/optimize-images.mjs` در زمان build با `sharp` برای هر تصویر می‌سازد:

- AVIF و WebP در سه عرض (۶۴۰ / ۱۰۲۴ / عرض اصلی)
- یک LQIP کوچک به‌صورت data-URI که تا رسیدن تصویر اصلی به‌عنوان پس‌زمینه نمایش داده می‌شود

نمونهٔ واقعی — تصویر قهرمان صفحهٔ نخست:

| نسخه | حجم |
| --- | --- |
| JPEG اصلی (fallback) | ۲۱۶ KB |
| WebP @1024 | ۶۱ KB |
| **AVIF @1024** | **۴۶ KB** |
| AVIF @640 (موبایل) | **۲۴ KB** |

روی موبایل یعنی **۲۴ KB به‌جای ۲۱۶ KB** — نزدیک به یک‌دهم.

## ۳. بهینه‌سازی‌های ریزتر ولی مؤثر

### ۳٫۱ جدا کردن زیرمجموعهٔ لاتین فونت

هر دو زیرمجموعهٔ Vazirmatn (عربی ۴۶KB + لاتین ۳۴KB) در یک `localFont` بودند، پس Next
**هر دو** را در هر صفحه `preload` می‌کرد: ۸۱ KB روی مسیر بحرانی.

ولی کل سایت فارسی است. حروف لاتین فقط در چند واژه ظاهر می‌شوند. حالا دو نمونهٔ جدا داریم:

```ts
const vazirmatn      = localFont({ …arabic, preload: true  });
const vazirmatnLatin = localFont({ …latin,  preload: false });
```

و در Tailwind پشت سر هم می‌آیند. مرورگر برای هر گلیف اولین خانوادهٔ دارای آن را برمی‌دارد،
پس فایل لاتین فقط وقتی دانلود می‌شود که واقعاً لازم شود.

**صرفه‌جویی: ۳۴ KB در اولین رنگ‌آمیزی هر صفحه.**

### ۳٫۲ `fetchpriority="high"` روی تصویر LCP

کامپوننت `Picture` با prop `priority` این‌ها را می‌گذارد:

```html
<img loading="eager" fetchpriority="high" decoding="sync" …>
```

بدون این، مرورگر تصویر قهرمان را هم‌رده با تصاویر پایین صفحه صف می‌کند.

### ۳٫۳ نسبت ابعاد تضمین‌شده (CLS صفر)

هر `<picture>` یا `aspect-ratio` ذاتی تصویر را دارد یا کلاس `aspect-*` فراخوان را. فضای
تصویر از لحظهٔ اول رزرو است، پس هنگام رسیدن تصویر چیزی نمی‌پرد.

> 🐞 **باگی که همین‌جا پیدا و رفع شد:** سبک درون‌خطی `aspectRatio` بر کلاس Tailwind غلبه
> می‌کرد، پس هر ۹ فراخوانی که `className="aspect-[4/3]"` می‌دادند بی‌اثر شده بودند و تصاویر
> با نسبت ذاتی رندر می‌شدند. حالا `Picture` وجود کلاس `aspect-*` را تشخیص می‌دهد و کنار
> می‌کشد.

### ۳٫۴ `optimizePackageImports` برای lucide-react

بدون این، وارد کردن یک آیکون کل بستهٔ آیکون را می‌کشید. با آن، فقط همان آیکون‌های
استفاده‌شده در باندل می‌آیند.

### ۳٫۵ Service Worker به‌جای CDN

وقتی دامنهٔ سوم ممنوع است، کش مرورگر تنها لایهٔ شتاب‌دهندهٔ باقی‌مانده است. راهبرد در
`scripts/postbuild.mjs`:

| منبع | راهبرد | دلیل |
| --- | --- | --- |
| پیمایش صفحات | network-first → cache → `offline.html` | محتوا همیشه تازه؛ آفلاین هم کار می‌کند |
| `/_next/static/` و فونت | cache-first | نامشان هش دارد، هرگز تغییر نمی‌کنند |
| تصاویر | stale-while-revalidate، سقف ۶۰ فایل | سریع، بدون پر کردن دیسک کاربر |

بازدید دوم تقریباً تماماً از کش می‌آید.

## ۶. آنچه هنوز اندازه‌گیری نشده

**Lighthouse در این محیط اجرا نشد** — نه مرورگر headless نصب بود، نه دسترسی شبکه به سایت
منتشرشده وجود داشت. اعداد بالا از خروجی build و اندازهٔ واقعی فایل‌ها می‌آیند، نه از حدس.

برای گرفتن عدد رسمی Lighthouse پس از انتشار:

```bash
# روی سایت زنده
npx lighthouse https://rahmaniho.github.io/Vokalahome/ \
  --preset=desktop --view

npx lighthouse https://rahmaniho.github.io/Vokalahome/ \
  --form-factor=mobile --throttling-method=simulate --view
```

یا بدون نصب چیزی: [PageSpeed Insights](https://pagespeed.web.dev/) ← آدرس سایت.

صفحاتی که حتماً باید سنجیده شوند:

| صفحه | چرا مهم است |
| --- | --- |
| `/` | ورودی اصلی، سنگین‌ترین تصویر |
| `/membership/` | سنگین‌ترین JS (Zod + QR) |

## ۷. اگر بعداً کند شد

سه سؤال، به‌ترتیب:

۱. **چیزی به باندل مشترک اضافه شده؟** خروجی `npm run build` را با جدول بخش ۴ مقایسه کنید.
   افزایش در ردیف «First Load JS shared by all» یعنی یک وابستگی به `layout.tsx` یا یک
   کامپوننت سراسری راه پیدا کرده.

۲. **کامپوننتی بی‌دلیل `'use client'` شده؟** هر `'use client'` مرز hydration می‌سازد.
   با `grep -rl "use client" src/components` فهرست را ببینید و بپرسید هرکدام واقعاً
   تعامل لازم دارد یا نه.

۳. **تصویری بدون `Picture` اضافه شده؟** `grep -rn "<img" src/` — تنها جای مجاز
   `Picture.tsx` است.
